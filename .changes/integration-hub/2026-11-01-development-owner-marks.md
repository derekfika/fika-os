# 2026-11-01 — Development dashboard: contrast fix and owner marks (#241 follow-on)

**Contrast fix.** The Hub defines only `--color-*`/`--space-*` tokens, not the `--fika-*` semantic names `development.module.css` used, so `background:var(--fika-action-primary)` resolved to nothing and the white "Pipeline" tab / "Refresh" labels vanished on the light page. The page now aliases every semantic token it uses onto Hub tokens (`.page{--fika-action-primary:var(--color-brand-primary)…}`); active tab and primary buttons are white on `#4f34c7` (about 7.2:1). A test resolves every `var()` in the module CSS and asserts at least 4.5:1 for primary, active-tab and secondary controls.

**Owner marks (owner-only, server-side).** `POST /api/development/marks` (and `GET ?issue=N` for history) with the same `requireAuthmodAdminContext` admission as `GET /api/development`, fail closed. Same-origin required, JSON only, 4 KB body cap enforced while streaming (no reliance on Content-Length), 20 writes/min/identity, strict zod validation (unknown keys such as `actor` are refused); the actor is derived from the AUTHMOD context, never the request. Kinds: checked, uat-accepted, uat-failed, deployed-staging, pushed-to-production, blocked-note, clear. UAT binds the server-verified serving staging SHA (a different build is refused with 409); a stale, partial, unavailable or errored snapshot is never treated or described as verified; with no verified SHA the owner must type the full SHA and it is stored and labelled unverified. Marks are owner-recorded assertions kept apart from verified evidence: they never change GitHub-derived status, and trigger no deploy, GitHub write or issue close. The snapshot carries `marks` beside the verified data; lifecycle steps show "Verified: X / Owner-recorded: Y", and My actions hides items the owner has checked or accepted (only while the mark is current) but still lists them with verified state under "Marked by you". Header label is now "Owner view".

**Persistence.** New server-side Firestore collection `development_dashboard_marks` (Admin SDK only; no client SDK, rules or index change): `issue-{N}` authoritative current state with a version, `issue-{N}/events/{id}` append-only history (id derived from the idempotency key, created never updated), and `current` a derived aggregate so the dashboard reads one document (no notes; issues with no marks left are removed; a GET with a missing aggregate computes it read-only from the authoritative documents and never writes, only append transactions rebuild it). Each write is one transaction: state, event, `integrationHubGovernanceAudit` record (doc id `audit_<eventId>`, `actorId` = Firebase uid, AUTHMOD id kept as `principalId`), aggregate entry; a replay writes nothing. Optimistic concurrency via `expectedVersion`.

Deployment: none. Staging verification of the new collection and routes is a separate governed step.
