# FEAT-033 — FIKA OS Design System Audit and Proposal

- **Status:** Review draft; no production components or application styles changed
- **Audit baseline:** `origin/main` at `29e19f4e1e386dc5f631b176e3f29bc6829b9651`
- **Scope:** Shared tokens and the current Hub, Menu Planning, Hospitality, CPU, Delivered-In and Logistics applications; also inspected Events Dashboard, Beverage Innovation and Ad-hoc Production as adjacent FIKA-branded surfaces.

## Executive summary

`docs/STYLE-GUIDE.md` is already an authoritative target standard. `shared/fika/tokens.css` supplies brand, semantic colour, typography, spacing, radius, shadow and layout variables. There is no shared React component library in `shared/fika` or `packages`; the user-facing applications define most buttons, controls, dialogs, tables and states locally.

The best building blocks are the Menu Planning `PlannerModal` focus-management pattern, Hub semantic control tokens, Delivered-In's recent standing-order controls, and Logistics' visit chooser focus trap and dedicated operational variants. These are useful references, not yet interchangeable components. They differ in markup, sizing, colour aliases, keyboard handling and CSS ownership.

The proposed direction is a small `packages/fika-ui` package layered over `shared/fika/tokens.css`, with composable, accessible primitives and explicit `standard`, `compact` and `touch` density variants. Keep application shells, domain layouts, planner grids, calendars and operational state in their owning apps. Build a non-production Storybook showcase with fixtures. Migrate incrementally after Karol and owner review.

## 2. Ten highest-impact inconsistencies

Ranked by the combination of cross-app frequency, accessibility/user impact and the chance of inconsistent future additions. These are audit findings, not a request to restyle untouched screens.

1. **No shared React primitives.** Each app owns button, form, dialog, status and feedback styles. A fix or new component does not naturally reach sibling apps. Evidence: `shared/fika` contains `tokens.css`; component implementations live under each app's `app/ui`, `components` or stylesheet.
2. **Primary-action colour is not consistently semantic.** The Guide says purple is the primary action. Hub `.primary` and Menu Planning `.button-mint` use turquoise/mint, while other areas use purple. Hospitality also overrides shared semantic aliases in `app/globals.css`. This blurs the action hierarchy and can undermine the approved brand rule.
3. **Semantic token sets are forked and overridden.** Shared token values are re-expressed as `--purple`, `--deep`, `--line`, or app-local `--fika-*`; some app root declarations replace shared semantic values. Hospitality's focus token is turquoise; Menu Planning has a mint global focus ring, while shared tokens define orange. A single token name can therefore mean different colours by application.
4. **Control sizing has no one exact contract.** The Guide permits normal buttons at 40–44px and compact buttons at 32–36px; tokens expose 44px, while inspected examples range from 34/36/38/40/42 to 46/50px. Touch/tablet contexts and desktop density need explicit variants and hit-area rules.
5. **Corner radii drift.** Shared tokens define 8, 14 and 20px plus pill. The Guide targets 8px controls, 12–14px cards and 16–20px modals. Examples include Logistics dialogs at 16px, Menu/Delivered-In cards at 16px, Ad-hoc Production error cards at 24px and planner controls at 5–12px.
6. **Spacing tokens do not fully represent the written rhythm.** The Guide lists 4, 8, 12, 16, 24, 32, 40, 48 and 64px. Shared tokens cover 4, 8, 12, 16, 24, 32 and 48px; 40 and 64px are absent. Many CSS files use literal 5, 6, 7, 9, 10, 11, 14, 18, 20 and 22px gaps/padding.
7. **Typography fallback and weight usage differ.** The Guide specifies Gilroy for interface text and Vim Heavy for short display headlines. Delivered-In's base stylesheet sets Arial; some other apps use local Gilroy aliases and local font-face declarations. Table/control typography also ranges from readable 14–16px to 9–12px in dense/legacy Logistics surfaces.
8. **Dialog accessibility varies between implementations.** Menu Planner has a full focus trap and restore path; the Hub confirmation modal does not trap Tab; other bespoke dialogs differ in initial focus and dismissal. A shared primitive can standardise keyboard behaviour while allowing a dense/touch content layout.
9. **Shared error and admission UI is duplicated.** Menu Planning and Logistics have near-parallel AdmissionError components and CSS; the Logistics copy substitutes raw colors, Arial, 24px radius and bespoke shadows. This is a concrete cross-app extraction candidate after approval.
10. **Status/feedback and responsive density lack a common contract.** Apps generally pair status labels with semantic colors, but badge sizing, announcement roles, empty/loading/error distinctions, table overflow/stacking and compact hit areas vary. Domain-specific dense planning is valid; those variants need documented limits and accessible touch/keyboard equivalents.

## 3. Proposed canonical component catalogue

This is a specification proposal derived from the existing Style Guide and token values. It adds no palette, font family or visual theme. Karol and the owner should approve it before implementation.

### Shared interaction rules

- Use Gilroy for interface text and Vim Heavy only for short prominent display headings. Use the existing font tokens and defined fallbacks.
- Use semantic `--fika-*` surface, text, border, action, focus and status tokens. Do not write raw colors when the shared equivalent exists. Status meaning always has text or an accessible name.
- Use `:focus-visible` with the shared focus token, a 3px outline and 2px offset. Never remove focus indication. Keep visible labels and programmatic names; placeholders are not labels.
- Respect `prefers-reduced-motion`. Loading controls disable duplicate submission and expose `aria-busy`; asynchronous status is announced with a restrained live region.
- `standard` is the normal control size. `compact` is permitted only for dense desktop tables/planners and must be at least 36px high. `touch` is at least 44px high with spacing between adjacent targets. Do not use compact density to shrink mobile targets.

## 4. Recommended architecture

1. Keep `shared/fika/tokens.css` as the canonical source for brand and semantic tokens. Reconcile the missing spacing aliases and define component-specific size aliases only after approval; retain old token names as compatibility aliases during migration.
2. Introduce `packages/fika-ui` as a private React/CSS package, following the repository's existing local package consumption pattern (`@fika/server-shared` uses a file dependency). Export named primitives and CSS; use CSS Modules or a namespaced layer, never global element selectors or app-wide resets.
3. Apps import the package directly. Do not import from sibling applications. Keep forms/domain models, Hub authorization, menus, booking flows, planner state and shell ownership in their current apps.
4. Keep deployment boundaries independent: package changes trigger package contract tests and typecheck/build for its direct consumers through an explicit dependency map; a consumer release still deploys only that app. Do not deploy all apps because one app adopts a button.
5. Keep React/React DOM as peer dependencies; publish no data, authentication or Firestore helpers from the UI package. Components must be SSR-safe and must not read browser globals during render.

### Component showcase plan

Create a Storybook workspace owned by `packages/fika-ui` with no production route or App Hosting backend. Include every variant/state at standard, compact and touch density; keyboard walkthroughs for dialog, tabs, select and date input; narrow/tablet/desktop viewports; contrast and reduced-motion examples; and FIKA token swatches with approved brand asset/font provenance. Stories use static fixtures only. CI runs Storybook build and focused accessibility/interaction checks; it does not deploy the showcase.

## 5. CI and lint safeguards

- Add package tests for accessible names, semantic roles, disabled/loading behaviour, focus trap/restore, Escape safety, reduced motion and responsive bounds.
- Add a scoped CSS lint configuration for `packages/fika-ui` and migrated component files: reject raw color literals when a semantic token exists, arbitrary control heights/radii, removed focus outlines and global resets. Permit documented exemptions for approved brand art, data visualization, third-party constraints and intentional timeline geometry.
- Add ESLint checks for native browser dialogs in production UI and for interactive non-semantic `div`/`span` patterns; require a reasoned exception for deliberate canvas/drag surfaces.
- Record an explicit app-to-package dependency map. Package CI validates direct consumers; unrelated app pipelines and deploys remain independent. Keep contract tests for every supported app framework/runtime boundary.
- Maintain a small exception file with owner, surface, reason and review date; no blanket path exclusions for an entire app.

## 6. Staged implementation plan

1. **Creative and token review:** Karol and owner approve palette roles, focus color, type hierarchy, spacing/radius/control scales, showcase scope and package direction.
2. **Foundations:** reconcile tokens with backward aliases, add `packages/fika-ui`, accessibility contracts and Storybook. Do not change application screens in this phase.
3. **High-reuse controls:** implement Button, Field/Input, Select, Checkbox/Switch and StatusBadge. Pilot in the showcase and one owner-selected low-risk app surface; preserve business logic and state.
4. **Dialog and feedback:** implement Dialog/Confirmation, InlineNotice/Toast, Loading/Empty/Error states. Migrate duplicated AdmissionError only after matching both sign-in and retry use cases.
5. **Data and navigation patterns:** add Table/List and Nav/PageHeader primitives; keep planner timelines, menu matrices, booking calendars and app shells domain-owned.
6. **Incremental adoption:** migrate only files directly touched by future work, then schedule app-by-app slices based on component duplication and risk. Leave active CPU work and Logistics V3 untouched until separately scheduled. Each app retains its own CI, release scope and staging/UAT gates.
7. **Deprecation:** after usage inventory and consumer CI coverage, mark app-local equivalents deprecated; remove only when all active consumers and legacy routes are verified.

## 7. Decisions for owner and Karol

- Confirm the authoritative visual roles where current app implementations differ from the Style Guide: purple primary action; orange focus ring; turquoise/mint limited to accent/surface use; Gilroy interface text and Vim Heavy display use.
- Approve exact size aliases proposed here (44px standard/touch, 36px compact desktop, 8px control radius, 12px card radius, 16px dialog radius, rows 48/40px) or adjust the specification before components are built.
- Confirm whether Events Dashboard is in the first implementation/migration cohort; its existing brand-foundation document says a shared package should wait until multiple active applications need it, while the current six-app inventory already contains repeated controls.
- Approve `packages/fika-ui` and Storybook as the ownership/showcase location, including the direct-consumer CI policy.
- Select the first low-risk application surface for the pilot. Recommendation: showcase first, then an owner-selected low-change screen; defer active CPU Production and Logistics V3 work.
- Confirm date-picker presentation should use native platform controls initially, with app-owned date policy and UK display, or request a custom accessible calendar after the showcase review.

## Audit limitations

This was a code/document inventory, not a full accessibility or visual conformance audit. No browser/assistive-technology measurements, colour contrast calculations, app-wide route inventory, or production checks were performed. Component examples are representative and files may contain additional local variants. Findings do not authorize a mass restyle or imply that every legacy deviation is a defect under the Guide's target-versus-legacy rule.
