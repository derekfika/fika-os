# CPUX Calendar v1 (#348)

Calendar reflects FIKA OS demand. Hub stages a separate delivery obligation alongside a successful Hospitality CPU order event; Menu Planning stages one obligation per affected day inside the existing publication transaction. The workers reload current authority. Calendar or Drive failure leaves the original order/publication committed. Neither worker creates a Production Order, changes permissions, or reads draft demand.

Hospitality events use the canonical booking ID and the site's approved Calendar. They use the exact current CPU order's routed lines with explicit production quantities and units; the approved full quote is checked under both invitees' Drive identities. Menu Planning events use the UK service date, collect all current published allocations and use Hub's verified OPLOC package for redirects/address evidence. A one-off keeps its published scoped identity and address. The PDF contains the entire day; Drive IDs are reserved durably by immutable publication revision before uploading. The attachment and private fallback link identify the same PDF. Withdrawal removes the guests, details and attachment from the same event and leaves a transparent organiser-only withdrawal marker. This preserves identity for an explicitly newer republish. All-day Delivered-In events use date-only values; timed Hospitality events use Europe/London.

Ongoing publication stages work for current and future UK service dates. A publication handoff repair does not queue a new Calendar obligation. A grouped booking marked Completed remains eligible with recorded Send to CPU history and a verified current order. Records missing explicit CPU quantities or units are held for correction in the source. A changed site Calendar or organiser requires operator review before moving an existing event.

The Hub worker follows authoritative Production Order changes. A quote-only refresh without a Production Order event does not yet schedule reconciliation. A cancellation requiring CPU review continues to follow the canonical production withdrawal decision. Complete and verify these booking workflow cases before enabling the live publisher.

## Readiness and configuration

No flags, secrets, schedulers, Calendars or Drive permissions are provisioned by this change. Keep existing PR #326 outbound publishing disabled for overlapping Hospitality demand. It has its own configuration and does not share the v1 Calendar bindings. Never run both outbound publishers for a booking. The owner has confirmed legacy scanner isolation; scanner changes are out of scope.

- On Hub and Menu Planning, explicitly configure `FIKA_CPUX_MIRROR_RUNTIME_IDENTITY` to each approved production runtime service account and `FIKA_CPUX_MIRROR_DWD_ISSUER` to the dedicated Workspace delegation account. The hosted runtime verifies the production project and exact service identity via metadata. Enable IAM Credentials and grant `iam.serviceAccounts.signJwt` on the dedicated issuer to the two approved runtime identities. The transport uses calendar.events (calendar.events.readonly for preview), drive.readonly and drive.file for the run-sheet writer. Verify delegated organiser write access for each exact Calendar and PDF reader access as the organiser and each intended invitee. Never configure these on staging.
- Supply `FIKA_CPUX_LOGISTICS_MAILBOX` on both apps after verifying the actual mailbox. CPUX is `cpux@fikacatering.com`. Hospitality uses `FIKA_CPUX_HOSPITALITY_CALENDARS_JSON`, an approved canonical OPLOC keyed JSON map with `{ "calendarId": "...", "subject": "..." }` per site. Menu Planning uses `FIKA_CPUX_DELIVERED_IN_CALENDAR_ID` and `FIKA_CPUX_DELIVERED_IN_CALENDAR_SUBJECT`. Do not use "primary", site names, attendee Calendars or guessed defaults.
- Set `FIKA_CPUX_DELIVERED_IN_RUN_SHEET_FOLDER_ID` to the approved private folder. Verify ancestry, effective reader access and no additional sharing. Folder verification fails closed on unknown/broad access. The code never grants permissions. Render through the existing PDF renderer configuration. If an approved quote is missing or either invitee cannot download it, correct the authoritative quote/ACL separately; the worker will not issue an incomplete invitation.
- `FIKA_CPUX_MIRROR_PREVIEW_ENABLED=true` permits the protected production read-only preview while writes remain off. `FIKA_CPUX_MIRROR_WRITES_ENABLED=true` is a separate live activation decision. Both reject staging, local, test and emulator modes. Prove staging isolation with mocked/emulated engineering tests and Luna's authorised non-writing staging checks. Do not add production identities to staging to test write paths.
- Ongoing worker: authenticated `POST /api/internal/cpux-mirror` on Hub with `{"action":"deliver","limit":3}`. Configure bounded production worker invocation only after owner approval. Menu Planning uses its existing authenticated `/api/internal/menu-publication-outbox` worker. Verify scheduler/worker operation explicitly; deploying source does not start a worker.
