# CPUX Calendar v1 (#348)

Calendar reflects FIKA OS demand. Hub stages a separate delivery obligation alongside a successful Hospitality CPU order event; Menu Planning stages one obligation per affected day inside the existing publication transaction. The workers reload current authority. Calendar or Drive failure leaves the original order/publication committed. Neither worker creates a Production Order, changes permissions, or reads draft demand.

Hospitality events use the canonical booking ID and the site's approved Calendar. Site Workspace mailboxes come from Hub's `booking-email-site-identities.ts` identity source; runtime JSON does not duplicate them. By default, the canonical mailbox is both the candidate Calendar ID and DWD subject. This is only a candidate binding: before any event read/write, Hub calls CalendarList as that delegated subject, requires the exact Calendar ID and `writer`/`owner` access, then verifies event organiser identity. A differing Calendar ID or delegated organiser must be explicitly configured per canonical OPLOC in `FIKA_CPUX_HOSPITALITY_CALENDARS_JSON` using only `calendarId` and/or `delegatedOrganizerMailbox`. Email equality alone never proves access, ownership or delegation. Verified bindings are recorded with the mirror identity; a changed or historically unverified binding requires operator review. They use the exact current CPU order's routed lines with explicit customer quantities and units; the approved full quote is checked under the organiser and both invitees' Drive identities. Menu Planning events use the UK service date, collect all current published allocations and use Hub's verified OPLOC package for redirects/address evidence. A one-off keeps its published scoped identity and address. The PDF contains the entire day; Drive IDs are reserved durably by immutable publication revision before uploading. The attachment and private fallback link identify the same PDF. Withdrawal removes the guests, details and attachment from the same event and leaves a transparent organiser-only withdrawal marker. This preserves identity for an explicitly newer republish. All-day Delivered-In events use date-only values; timed Hospitality events use Europe/London.

Ongoing publication stages work for current and future UK service dates. A publication handoff repair does not queue a new Calendar obligation. A grouped booking marked Completed remains eligible with recorded Send to CPU history and a verified current order. Records missing explicit CPU quantities or units are held for correction in the source. A changed site Calendar or organiser requires operator review before moving an existing event.

The Hub worker follows authoritative Production Order changes. A quote-only refresh without a Production Order event does not yet schedule reconciliation. A cancellation requiring CPU review continues to follow the canonical production withdrawal decision. Complete and verify these booking workflow cases before enabling the live publisher.

## One-time catch-up

Both endpoints accept explicit inclusive date ranges of up to 14 days, starting on or after **2026-11-09**. Use the approved production HTTPS app origins and the internal token. The Menu Planning endpoint additionally keeps the existing hosted session admission. Treat response evidence as private operational data.

1. Preview Hub with `{"action":"catch-up","from":"2026-11-09","through":"2026-11-15"}`; preview Menu Planning `POST /api/internal/cpux-mirror` with `{"from":"2026-11-09","through":"2026-11-15"}`. No `approveHash` means read-only: no booking, order, Calendar, Drive, checkpoint, or approval writes. Hub pages ten bookings at a time; feed its exact returned `nextCursor` as `after` when previewing the next batch.
2. Review event dispositions, stable IDs, organisers, attendees, quote file IDs/run-sheet revision and folder, skipped/missing/ambiguous rows and expected notifications. Existing events match deterministic ID and exact shared provenance only. Unknown older events cannot be safely adopted based on title/date; review any earlier outbound publication evidence before enabling writes.
3. After separate owner approval of that exact batch, configure its reviewed hash in `FIKA_CPUX_HOSPITALITY_CATCH_UP_APPROVAL_HASH` or `FIKA_CPUX_DELIVERED_IN_CATCH_UP_APPROVAL_HASH`, and submit the same request and cursor with `approveHash`. If source identity/revision, recipients, mapping, date range or skipped evidence changes, preview again. Each successful event records a checkpoint by approved hash/event ID. An interrupted batch resumes with the same request; already applied revisions are read back and skipped without sending another invitation. A changed revision needs a new approved preview.
4. Record scanned, eligible, created, updated, unchanged/skipped and failed counts from responses. Revisit failures through the approved batch, including any missing document or ambiguous identity. Do not advance the Hub cursor past unresolved failures without recording them. Remove the one-time approval hashes after reconciliation.

Disable the write flags and pause any dedicated Hub worker to stop outbound delivery. Leave canonical handoffs, publication records, pending delivery evidence and published Drive revisions intact. Existing events are historical evidence; retiring or cancelling them is a separate controlled operation. No automatic catch-up or recurring scan is introduced.
