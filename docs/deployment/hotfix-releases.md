# Governed production hotfix releases

## Status

The dedicated `fika hotfix` route is integrated with the governed release lock, journal, App Hosting submission, verification, smoke, rollback and append-only ledger. Ordinary `fika deploy` remains main-only. The route is opt-in per release through `--activate-hotfix` plus an explicit approval hash; this change does not alter GitHub protections, production configuration or serving applications. The route fails closed until the exact branch protections and candidate evidence can be verified.

## Source and review model

1. Read the exact serving production source SHA and rollout from the governed App Hosting target; verify the repository, application root, successful rollout, ready build, disabled automatic rollouts, and 100% traffic. This SHA is the only permitted branch point.
2. Create a unique `hotfix/prod/<app>/<release-id>` branch at that source. The reviewed manifest is kept in the PR body and bound to the source-committed app changelog fragment using its canonical SHA-256 digest. It binds the app, environment, release ID, baseline SHA and rollout, production configuration digest, approved application paths and their blob IDs, and reviewed PR head. Release IDs are immutable and are never reused. `fika hotfix inspect <app> --prod --release-id <id>` prints the current baseline and manifest template without creating a branch or changing state.
3. A protected PR targets only that branch. The merge commit must have the verified serving source as its first parent and be the exact merged PR commit. Require at least one non-author approval, dismiss stale approvals on new commits, require the exact `Workflow / merge-gate` check for the candidate SHA, enforce rules for administrators, prohibit force pushes and branch deletion, and configure no bypass actors. If branch/ruleset protection or its effective scope cannot be read and verified, stop.
4. CI checks out and validates the exact source. The observed `Workflow / merge-gate` run must succeed for the exact merge SHA. The validator rejects unlisted files, other applications, runtime configuration changes, dependencies/lockfiles, missing scoped changelog evidence, and a PR-body manifest that does not match the source-committed manifest digest.
5. The release record binds app, candidate SHA, first-parent baseline, baseline rollout, branch, PR, approvers, exact check-run URL/SHA, manifest and diff hashes, configuration digest, operator, exact-source production approval, reason, and validation evidence. Approval evidence is bound to the app and candidate SHA, not a branch name or mutable tag.

`fika hotfix deploy <app> --prod --release-id <id> --sha <merge-sha>` is read-only preparation by default. Execution requires `--execute --activate-hotfix --approve-hash <exact-plan-hash> --reason <reason>`. The command first acquires the existing app/environment lock and runs the existing release prestate, journal, backend identity, operator authentication and serving-source checks. It then re-reads the branch, PR, protection/ruleset, checks, manifest, current serving SHA/rollout and effective configuration immediately before the existing durable intent is appended. A pending/unknown journal, changed source or rollout, active Firebase build/rollout/operation, config drift, missing approval, or changed tree hash stops before submission. It submits only the exact candidate SHA to the one mapped application backend. Existing smoke, 100% traffic verification, append-only release ledger, rollback selection and ambiguous-attempt recovery remain authoritative. A pending hotfix intent can be resumed only through the dedicated route with the original release ID and approval hash, and its evidence is revalidated against the journal baseline. Hotfix metadata is added to the existing intent, journal and completed release record; there is no second lock or release ledger.

## Main reconciliation and ancestry

Production records retain the candidate's baseline as first parent, making the production-to-hotfix ancestry explicit. A successful hotfix writes `mainReconciliation: pending` to the app's append-only release history. The next normal production promotion for that app is held until a protected, green main PR records the hotfix source SHA and diff hash and incorporates equivalent app-scope content. The reconciliation event is appended to the same application history and references the merged main PR/check. Release planning verifies that event before accepting a main candidate. Other applications are unaffected. Rollback remains an explicit selection of an earlier verified record and keeps the existing source, CI, lock, journal and serving checks.

If main already contains equivalent changes but not the production hotfix commit, reconciliation uses a protected main PR that adds a small immutable lineage manifest referencing the hotfix commit and diff hash; it does not rewrite main ancestry or force-merge a no-diff branch. That manifest is checked against the app-scope tree hash before the hold is removed. Future production source remains main-derived and carries the recorded lineage.

## Checks and current blockers

`tools/workflow/hotfix.mjs` contains the policy boundary and `tools/workflow/hotfix-release.mjs` reads production/GitHub evidence. The current connected GitHub identity can read repository administration endpoints, but API evidence shows no matching rulesets and no effective branch rules for hotfix targets. The current `main` protection has strict `Workflow / merge-gate` status but zero required human approvals and no stale-review dismissal; that does not satisfy the hotfix policy. Do not claim the hotfix branch governance is verified until an administrator applies and the API confirms the exact settings below.

For the retained candidates, the repository administrator must create two active rulesets: `refs/heads/hotfix/prod/hub/*` and `refs/heads/hotfix/prod/hospitality/*`, each with no exclusions or bypass actors. Require pull requests, at least one approval, dismiss stale approvals on new commits, require strict `Workflow / merge-gate` status from GitHub Actions integration `15368`, require workflow `.github/workflows/validate.yml` from repository `derekfika/fika-os` (repository ID `1297704019`) at `main`, block deletion and non-fast-forward updates, and enforce for administrators. GitHub ruleset-required workflows ignore branch/path filters in the workflow's supported events, so `validate.yml` can still be required for these branch targets despite its existing `main` filter. The validator also checks paginated ruleset listings and the effective rules returned by GitHub for the exact release branch. The repository role currently reports `admin: true`; [GitHub's ruleset permission guide](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository) says repository admins or custom roles with `edit repository rules` can manage repository rulesets.

After the exact ruleset is active, an administrator can seed a release branch at the verified serving SHA, prepare a PR and source-bound manifest, then run the read-only command. A production operator must review its plan hash and explicitly execute the matching command. This task does not change protections, activate a release, or deploy production. A release is never eligible from an arbitrary SHA, local branch, pull-request head, unprotected branch, stale serving baseline, or CI attached to another commit.
