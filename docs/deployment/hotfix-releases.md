# Governed production hotfix releases

## Status

This describes the proposed application-specific production hotfix route. The normal `fika deploy` route remains main-only. This implementation does not modify GitHub protections, change production runtime configuration, deploy, or turn on a hotfix deploy command. A release branch is ineligible until all of the governance evidence below is available and an owner approves activation of the route.

## Source and review model

1. Read the exact serving production source SHA and rollout from the governed App Hosting target; verify the repository, application root, successful rollout, ready build, disabled automatic rollouts, and 100% traffic. This SHA is the only permitted branch point.
2. Create a unique `hotfix/prod/<app>/<release-id>` branch at that source. The release manifest binds the app, environment, release ID, baseline SHA and rollout, configuration digest, approved paths and their blob IDs, and the reviewed PR head. Release IDs are immutable and are never reused.
3. A protected PR targets only that branch. The merge commit must have the verified serving source as its first parent and be the exact merged PR commit. Require at least one non-author approval, dismiss stale approvals on new commits, require the exact `Workflow / merge-gate` check for the candidate SHA, enforce rules for administrators, prohibit force pushes and branch deletion, and configure no bypass actors. If branch/ruleset protection or its effective scope cannot be read and verified, stop.
4. CI checks out and builds the exact candidate SHA. It runs the app's tests, typecheck, production build, applicable shared-contract and emulator tests, dependency/security checks, and a hotfix path/configuration policy check. The merge gate must verify the manifest against the actual tree and reject unlisted files, other applications, runtime configuration changes, and dependency/lockfile edits unless a separately reviewed manifest explicitly names an allowed shared dependency and all consumers are tested.
5. The release record binds app, candidate SHA, first-parent baseline, baseline rollout, branch, PR, approvers, exact check-run URL/SHA, manifest and diff hashes, configuration digest, operator, exact-source production approval, reason, and validation evidence. Approval evidence is bound to the app and candidate SHA, not a branch name or mutable tag.

The deploy command must first acquire the existing app/environment lock and run the existing release prestate, journal, backend identity, operator-authentication and serving-source checks. It then re-reads the branch, PR, protection/ruleset, checks, manifest, current serving SHA/rollout and effective configuration immediately before the existing durable intent is appended. A pending/unknown journal, changed source or rollout, active Firebase build/rollout/operation, config drift, missing approval, or changed tree hash stops before submission. It submits only the exact candidate SHA to the one mapped application backend. Existing smoke, 100% traffic verification, append-only release ledger, rollback selection and ambiguous-attempt recovery remain authoritative. Hotfix metadata is added to the existing intent, journal and completed release record; there is no second lock or release ledger.

## Main reconciliation and ancestry

Production records retain the candidate's baseline as first parent, making the production-to-hotfix ancestry explicit. A successful hotfix writes `mainReconciliation: pending` to the app's append-only release history. The next normal production promotion for that app is held until a protected, green main PR records the hotfix source SHA and diff hash and incorporates equivalent app-scope content. The reconciliation event is appended to the same application history and references the merged main PR/check. Release planning verifies that event before accepting a main candidate. Other applications are unaffected. Rollback remains an explicit selection of an earlier verified record and keeps the existing source, CI, lock, journal and serving checks.

If main already contains equivalent changes but not the production hotfix commit, reconciliation uses a protected main PR that adds a small immutable lineage manifest referencing the hotfix commit and diff hash; it does not rewrite main ancestry or force-merge a no-diff branch. That manifest is checked against the app-scope tree hash before the hold is removed. Future production source remains main-derived and carries the recorded lineage.

## Checks and current blockers

`tools/workflow/hotfix.mjs` implements the fail-closed candidate evidence checks as a pure policy boundary with fixture tests. It is not called by `fika deploy`, so existing production eligibility remains unchanged. Before a deploy integration can be merged or enabled, the owner must approve the route and repository administrators must configure and independently verify the protected branch/ruleset pattern plus a workflow that runs the gate on those targets. During this task the GitHub integration did not grant access to `main` classic branch-protection details and no matching repository ruleset was observable. No candidate can claim real GitHub PR review or exact-source CI while that remains unresolved.

Test release lock contention, pending journal and rollback behavior against the existing release fixtures as part of the later deploy integration. A production release is never eligible from an arbitrary SHA, local branch, pull-request head, unprotected branch, stale serving baseline, or CI attached to a different commit.
