# Hosted staging Drive identity — 13 November 2026

Complexity: High. Recommended model: Sol / High. Reason: Workspace credentials, signed food-safety artifacts and a shared cross-app provider.

## Decision — revised for no additional Workspace licence

Preferred: a dedicated FIKA OS Staging Shared Drive and a new non-DWD service account in `fika-os-dev`. The three staging runtimes mint five-minute ordinary service-account Drive tokens through IAM Credentials. No user impersonation, service-account key, refresh token or paid Workspace user is required. The target SA has access only to the staging Shared Drive. Production identities/configuration are unchanged.

Fallback: a dedicated free Google account with ordinary offline OAuth and access only to the existing approved staging folder. Do not use Derek's account. This needs external sharing to be allowed and an external OAuth client (an internal Workspace-only client cannot authorize a Gmail account). It adds account recovery/MFA, storage quota and OAuth consent/token maintenance, so it is less maintainable than the Shared Drive model.

| Option | Decision |
|---|---|
| Shared Drive + direct non-DWD SA | Preferred, conditional on tenant creation and service-account membership policy. Keyless, organization-owned files, no extra user licence. |
| Dedicated free Google user + OAuth | Supported fallback, no new paid licence. Existing folder remains My Drive; only this isolated account's grant is used. |
| New paid Workspace user | Rejected by owner; not required. |
| DWD with a staging subject/folder | Rejected. DWD scope permits domain user impersonation; a folder setting does not restrict the issuer's authority. |

Official sources: https://knowledge.workspace.google.com/admin/drive/set-up-shared-drives-for-your-organization (includes Business Starter, with limitations); https://developers.google.com/workspace/drive/api/guides/about-shareddrives ; https://docs.cloud.google.com/iam/docs/reference/credentials/rest/v1/projects.serviceAccounts/generateAccessToken .

## Provider and consumers

`drive-owner` supports a verified staging mode only after metadata-server project verification, consistent `fika-os-dev` claims, absence of both DWD secrets, a keyless direct-SA Drive token or isolated user OAuth refresh with exactly Drive scope, immutable Drive user permission-ID/email verification, approved root ACL verification, and denial of 1–10 production sentinel IDs. No DWD/local fallback. The default remains disabled.

All app/OPLOC owners resolve to the staging account/root in this mode. Hospitality matrix destinations and new Hub grouped-quote destinations use the environment staging root rather than production site settings. Explicit menu/quote folder overrides must remain descendants. CPU signed PDF downloads and shared menu templates/results must pass bounded ancestry checks; shortcuts/cycles/outside-root IDs fail. Historical stored artifacts are not migrated or rewritten. Generic stored-link responses and Calendar quote redirects remain blocked in staging: only the CPU signed-document gateway and matrix persistence readiness opt into verified staging operations. This avoids exposing copied production Drive URLs through a user's own browser identity. Hub grouped quote POST remains on its existing containment hold; shared provider support does not enable its notifications or retries.

The user account must have no production group/shared-drive/file access. Root checks and sentinel denials supplement that admin-established account boundary; sample denial does not prove absence of every possible production ACL. An administrator must inspect memberships and actual shares.

No Firestore schema, outbox, publication, signature or production quantity changes. Verification is read-only except the ordinary authorized staging signing workflow. Each verification uses bounded requests: runtime metadata, token mint/refresh, Drive about, root metadata/ACL (and Shared Drive membership ACL) and up to 10 denial probes; ancestry adds at most 32 metadata reads. No background polling, durable per-read audit writes, or token logging. There is no success cache, so changed ACLs/credentials fail on the next verification.
