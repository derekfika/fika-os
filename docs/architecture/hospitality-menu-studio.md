# ADR — Hospitality Menu Studio content authority and Rotations cutover
+
+Proposed for [#586](https://github.com/derekfika/fika-os/issues/586) on 18 November 2026. Source inspection used `origin/main` at `e871e8e3073b2cefc621391183328d290072ddff`. This records decisions and prerequisites for implementation and cutover. Live data, IAM, serving versions and authenticated operational acceptance were outside this inspection.
+
+## Decision
+
+Use a standalone application and server-side content store for Hospitality Menu Studio. Studio owns dish identities and immutable revisions, customer and kitchen descriptions, fixed assortments, seasons, collection composition, static and six-week sections, and content publication. Hub owns AUTHMOD, canonical OPLOCs and sellable Items, effective Prices and Offerings, VAT, minima, visibility, ordering and allocation rules, booking acceptance and the canonical production handoff. CPU owns allergen review and signed releases, and accepted production work. Menu Planning continues to own its general Dish Library and published production menus.
+
+A booking path follows Studio content publication → verified Hub activation → Hospitality request → Hub acceptance with frozen menu evidence → existing quote and explicit Send to CPU → canonical Production Order and Fulfilment Requirement. Studio never issues a Production Order or queues fulfilment. Publication and special collection activation are separate business commands.

+## Publication, safety and consumer contracts
+
+- **Content and schedule.** Use stable IDs and independent optimistic versions for drafts; record exact dish revisions in menu files and their immutable publications. Autosave acknowledges persisted versions, retains edits after conflict or transport failure, and uses actor-bound idempotency keys on retries. Publish a fully resolved immutable revision with explicit scope, base publication, source draft version, actor, reason and effective London business date. Materialise a full publication from a scoped edit so consumers can resolve one package; a stale base requires review again. Use non-overlapping season date ranges and explicit supersession where amendments affect later scheduled content. A single London anchor Monday supplies every rotating section's six-week cycle; static sections ignore the week. Portable date-only arithmetic preserves pre-anchor wrap, DST and year rollover.
+- **Review before publication.** Add a CPU-owned pre-publication source to the existing checker, role-gated signing and release lifecycle. The review subject is the exact immutable Studio dish ID, revision and source hash. It can be submitted from the draft using an authenticated, bounded handoff and does not materialise production demand. CPU binds both distinct authorised person identities, roles and signatures to the frozen matrix and subject, with current/revoked state and immutable lineage. Verify signer separation explicitly in the new CPU path; existing role checks alone do not prove different people. Studio and Hub receive only verifiable readiness and source/release references. They do not create reviews, stamp approvals or copy signature images. New or material revisions require new review; equivalent evidence may advance only through CPU's explicitly verified equivalence/rebinding path if implemented for Studio. An order-level signature or a PDF from another source never substitutes for this check.
+- **Package and activation.** Keep a versioned, source-bound package descriptor with publication ID, schema, scope, effective date, source revision/draft, supersession, author, content hash, object generation and bounded size. Validate strict version and payload, expected project/dataset, source identity, checksum and current CPU release references. On gzip storage, read with `decompress: false`, check raw compressed bytes before decompression, and cover the actual storage adapter with a roundtrip test. Studio commits content/history with an outbox obligation. Hub verifies and stages immutable bytes, then commits the activation head and actor-bound receipt/event atomically with an expected generation. Keep out-of-order and changed-payload retries from overriding a current activation. Record pending/published/activated/withdrawn states independently. Staff-only collection use is authorised; public collection activation separately checks current Hub catalogue eligibility and food-safety evidence.
+- **Current authority.** Hub resolves its own verified package/activation by stable Item and London event date and intersects it with the canonical OPLOC's catalogue and rules. Hospitality consumes a customer projection containing permitted choices and approved customer text. The server-only package and frozen booking/CPU evidence carry kitchen text and proof. Public page, API, cache and quote schemas should allowlist fields so internal text cannot leak. Booking submit reads the activation and authoritative current safety fence for the selected revisions at Hub's transaction boundary; an outdated browser view never validates a booking. No synchronous Studio request is required for the ordinary booking path. CPU and Hub must provide a revocation protocol that fences new acceptance before the changed review can supersede the old one. A delayed outbox event or a cache TTL by itself leaves a window of unsafe acceptance. If a current authoritative fence cannot be established, fail closed. Distinguish missing-but-rebuildable, stale/withdrawn, integrity failure and unavailable evidence. Rebuild missing verified derivatives through an explicit retry or repair; a read never publishes, and integrity failure never falls back.
+- **Frozen booking evidence.** Accept customer intent (stable selection IDs and quantities), then resolve and freeze the relevant package/publication, season/collection, section/week, dish revisions, snapshot descriptions, components and verified release references server-side with the Booking revision. Maintain the same shape in the approved Quote's evidence as needed for handoff, with customer-safe quote rendering. Retry of an accepted request returns the accepted snapshot. Non-material amendments preserve previously selected revisions; deliberate changes use the applicable new content and existing quote/production amendment rules. Preserve historic snapshots and no-CPU paths. Distinguish sellable quantity/unit, per-unit component quantity/unit and total production quantities. For a fixed-count case such as 4 boxes of 24 pieces, the snapshot stores 4 boxes plus the per-box breakdown and yields 96 total pieces. Do not add weights to piece counts or use guest count as box count. CPU renders from the frozen typed snapshot by canonical line/dish identity, and retains separate booking notes. Logistics continues to consume the existing Fulfilment Requirement.
+- **Impact and audit.** Derive affected future bookings from current Hub canonical status/meaning (review confirmed/approved and sent-to-CPU paths), London event dates and stable prior selection identity. Scan only bounded indexed dates/status/scope and paginate or report results as incomplete. Old bookings without mappable selection data or unavailable queries yield an explicit warning, not a zero count. Supply read-only, authorised, minimal booking/selection details. Publication never edits, substitutes, cancels or resends those bookings. Durable publish, activation, withdrawal, import and cutover records carry actor, source, entity/version, correlation/request ID, timestamp, reason and before/after references; outbox retries reuse the same evidence. Ordinary reads use bounded manifest/package and ID lookups, and incur no audit writes, broad listeners or new polling jobs. Measure source-write, activation and customer visibility latency plus cold/warm read volume in acceptance.

+## One-way cutover
+
+1. **Inventory.** Under separate data-access authority, capture an internally consistent export of the company head, all retained revisions and commands, both link directions, explicitly scoped dishes (including unmapped bank dishes), and referenced canonical Hub Items plus relevant identity redirects. Include archived reference identities and every future legacy activation. Record environment, capture time, source head version and checksums. Recheck the head and source identities/revisions at freeze. Keep commands and original published bytes as source evidence. Export no customer, booking, quote, order or signed-record payloads for conversion. Run booking compatibility/impact checks separately against authorised, bounded projections.
+2. **Dry run and resolve conflicts.** Reproduce the legacy canonical JSON revision hash and validate exact reference and activation lineage. Report malformed/duplicate IDs, revision/hash mismatch, missing frozen recipes, broken link pairs, Item redirects/withdrawals, missing classifications/text, non-six-week schedules and collisions with pre-existing Studio source keys. Preserve stored historical Item IDs even when aliases resolve for future eligibility. Keep old group order, category IDs, Item associations, week order, anchor and original date windows. Copy exact Hospitality-owned identities into Studio; use a read-only exact-revision reference and provenance for `SHARED` dishes, without transferring authority over their Menu Planning content. Treat unmapped internal/unknown classifications, old general description, free text, ingredients, absence of structured fixed units and historical allergen facts as explicit review states. Never infer customer-safe text, Hot/Cold, dietary suitability, fixed assortment quantities or verification. Preserve legacy row rules as source evidence and record where Hub's current commercial rules must be mapped and checked. Compare deterministic plans from the same export, prove retry identity and refuse divergent candidates under the same source key.
+3. **Stage and compare.** In the verified isolated environment, import immutable historical provenance and inactive Studio drafts with source keys (provider, legacy revision and hash). Verify checksum and referential coverage, dry-run event-date parity across current and scheduled periods, and compare expected site eligibility, including affected and excluded Items. Accept administrator/reviewer sign-off only through actual AUTHMOD/checker sessions and source-bound evidence. An incomplete draft can be imported but cannot be activated. Keep a verified legacy read adapter for dates/revisions before the agreed switchover and readers for historical booking/order shapes that lack Studio fields. Keep an explicit activation record for every qualifying date/scope; missing, corrupt or stale Studio packages after switchover cannot quietly restore live legacy content.
+4. **Fence and activate.** After acceptance, pause legacy writes on Hub's save/publish/link mutation seams and the Menu Planning dish-create path before its first catalogue write. Drain in-flight commands and verify head, link and dish versions against the approved inventory. While both live writer paths are fenced, reconcile differences, stage verified Studio packages and the matching Hub activation generation, and select a London event-date boundary. Resolve all later scheduled legacy activations explicitly before switching. Keep Studio's live publication gate closed until Hub positively records legacy retirement and the accepted activation generation. Switch the Hub acceptance/read pointer with compare-and-set, retain the original route for authorised legacy/history reads, then enable Studio as the only writer and route current authoring there. Use durable phases and receipts, with a clear retry from each checkpoint. A failed command or a changed source leaves the pending generation identifiable and consumers on the last authorised mode or explicitly unavailable. Use read-only shadow comparisons before the switch, with no dual writer or live booking side effect.
+5. **Recover.** Preserve the legacy head, originals, verified activation generations and writer fence. A rejected or pre-switch run can be resumed from the recorded state or unwound with an audited fence release and version recheck. After switchover, pause acceptance of affected Studio content, fence Studio changes if needed, and explicitly activate a previously verified, still safe package or repair forward. Restore legacy live reads only through an authorised pointer change with current eligibility and evidence. Re-enable the legacy writer only if Studio is fenced and a verified no-divergence check proves there are no accepted Studio writes to reconcile. Otherwise keep one writer and reconcile forward. Historical Booking, Quote, Production, signing and fulfilment records remain immutable throughout.
