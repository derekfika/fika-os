# RCoA Hospitality mapping

The public booking entry is `/rcoa`. It uses RCoA branding through the shared Hospitality site configuration and preserves the public RCoA request flow. The manager route remains the existing `HospitalityDashboard`; it uses the normal booking list, calendar, quote/PDF/Drive, confirmation, amendment, cancellation, Production Order/CPU, allergen matrix, run-sheet and output workflows. There is no RCoA-specific manager dashboard presentation layer.

## Source and canonical record

| Legacy field or behavior | FIKA OS representation |
| --- | --- |
| RCoA organization identity | `portalSiteId: "rcoa"`, display label `RCoA Hospitality`, theme in `portalSites` |
| Legacy booking reference | Stable `sourceBookingId` beginning `RCOA-`; canonical booking ID is generated by the existing Hospitality booking service |
| Event type, event date/time, guest count, room/floor/delivery point | Existing canonical booking service fields |
| Requester and invoice reference | Existing canonical client fields and immutable source payload |
| Menu item, price, quantity, choices, serving notes | Server-rebuilt commercial line snapshot from the generated RCoA catalogue; client prices and site identity are rejected |
| Dietary counts, allergy notes, severe-allergy acknowledgement, free-text notes | Existing canonical booking dietary and acknowledgement evidence; missing menu allergen data stays unrecorded |
| VAT and confirmation wording | Source VAT rate `0.20`; quote remains indicative and the Hospitality team confirms VAT/labour/equipment as applicable |
| Standard, large-event, dietary, item notice periods | Public request guidance in Europe/London time; the shared booking lifecycle remains authoritative |

`generated/rcoa-hospitality-menu.v1.json` is a deterministic conversion of the 43 legacy menu records. The source provides no structured dietary or allergen declaration; the generated validation report records this gap, and empty arrays must not be treated as `CLEAR`. RCoA feedback remains disabled. Legacy Sheets, Gmail, Drive, and Apps Script calendar persistence are not the source of current operational truth.

The Integration Hub continues to own canonical booking persistence and downstream Production handoff. RCoA items retain source ID/provider evidence and remain site-scoped compatibility snapshots until explicitly promoted into the shared canonical Hospitality catalogue.

## Governed access and setup

Before enabling production requests or manager access:

1. Configure `FIKA_RCOA_OPLOC_ID` in the Hospitality app with the canonical active RCoA OPLOC ID.
2. Configure a confirmed Integration Hub `provider-location` source mapping with `sourceIdentifier: "rcoa"` and that same canonical OPLOC ID. The integration rejects label-only mappings.
3. Configure `FIKA_RCOA_NOTIFICATION_RECIPIENTS` (or the shared `FIKA_BOOKING_NOTIFICATION_RECIPIENTS`) for internal request notifications. RCoA does not inherit MNK's default notification address.

The manager access proxy exposes the RCoA portal only when the Hub-authorised OPLOC exactly matches the configured ID. Missing configuration is fail-closed. No OPLOC UUID or recipient address is hardcoded by this port.
